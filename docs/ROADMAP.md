# ClimbPose Lab — Roadmap

> แผนพัฒนาจาก v0.2 (ไฟล์เดียว) ไปสู่ v1.0 ที่ใช้งานจริงได้
> โมดูล M00–M17 อ้างอิงจาก [ARCHITECTURE.md](ARCHITECTURE.md)
> เวลาเป็นค่าประมาณสำหรับคนทำงานคนเดียว

## เป้าหมาย v1.0

นักปีนอัดคลิปด้วยมือถือ เปิดเว็บ แล้วได้ภายในไม่กี่นาที:

1. รู้ว่าแต่ละ attempt **ส่งหรือไม่ส่ง** และไปถึงโฮลด์ไหน
2. เห็น **จังหวะที่หลุด** พร้อมเหตุผลเชิงท่าทางและคำแนะนำที่โค้ช/นักปีนเกรดสูงเห็นด้วย
3. เทียบกับ **ครั้งก่อนบนรูทเดียวกัน** ว่าดีขึ้นตรงไหน
4. ได้ **คลิปสวยพร้อมโพสต์** (Reels/TikTok)

ทั้งหมดโดยวิดีโอไม่ออกจากเครื่อง

### ตัวชี้วัดความสำเร็จ (วัดด้วย eval script บนชุดคลิปที่ติดป้ายแล้ว)

| ตัวชี้วัด | v0.2 (ประเมินจากการดูด้วยตา) | เป้า v1.0 |
|---|---|---|
| ตรวจ attempt ครบและไม่เกิน | ถูกใน 4 คลิปทดสอบหลังแก้ | ≥ 95% ของ attempt |
| ขอบ attempt คลาดเคลื่อน | ~0.5–1 วิ | ≤ 0.7 วิ |
| ตัดสินส่ง/ไม่ส่งถูก | ถูกหลังแก้กติกา (3 คลิป) | ≥ 90% |
| เฟรมที่ซ้าย/ขวาถูก (หันหลังให้กล้อง) | ไหล่ 99.5%, ขา 87–97% | ไหล่ ≥ 99%, ขา ≥ 95% |
| เฟรม crux ห่างจากที่โค้ชเลือก | ยังไม่ได้วัด | ≤ 0.5 วิ ใน ≥ 80% |
| คำแนะนำที่โค้ชเห็นด้วย | ยังไม่ได้วัด | ≥ 70% |
| เวลาวิเคราะห์ (คลิป 40 วิ, M3) | ~90 วิ ที่ 30 fps | ≤ 45 วิ |
| เวลา export (คลิป 40 วิ) | ~30 วิ | ≤ 30 วิ |

## Phase 3 · ความแม่นยำ (2–3 สัปดาห์, เรียงตามผลกระทบ)

ลำดับจริงตัดสินจากตัวเลข eval ใน Phase 2 — ตัวที่ห่างเป้ามากสุดทำก่อน

| งาน | โมดูล | ปัญหาที่เคยเจอ |
|---|---|---|
| ✅ จัดกลุ่มโฮลด์ (re-grip = โฮลด์เดียว) ทั้งใน logic ไม่ใช่แค่ตอนวาด — `groupHolds` รัศมี 12 ซม., นับโฮลด์จริง/ท่าขยับแยกกัน, เป้า crux ไม่ใช่โฮลด์ที่จับอยู่ | M07 | โฮลด์ใหญ่ถูกแตกเป็น 5 รายการ ทำให้ตัดสินส่งพลาด |
| ✅ ลด drift ชดเชยกล้อง: similarity (เลื่อน+ซูม+เอียง) เทียบ keyframe + re-anchor — คลาดเคลื่อนจาก 13–75 ซม. เหลือ 1–19 ซม. (เทียบ OpenCV); ที่เหลือ: homography สำหรับมุมมองเอียงมาก (IMG_4497) | M03 | IMG_4497 โฮลด์ช่วงท้ายดูสูงกว่าจริง |
| 🔶 ขาสลับตอนสะโพกบิดข้าง — เพิ่มเงื่อนไขฝั่งลำตัว (ขาซ้ายควรอยู่ฝั่งซ้ายของแกนตั้งฉากกับกระดูกสันหลัง): ตรวจด้วยตา 7 จุดที่เปลี่ยน ถูก 6 ผิด 1 (ขาที่ยกถูกบังอยู่หน้าลำตัว); ยังไม่มีป้ายซ้าย/ขวาสำหรับวัดทั้งคลิป | M04 | IMG_4016 วินาทีที่ 3.7 |
| 🔶 พื้นและ attempt ในคลิปที่เดินเข้าออกกล้อง — แก้แล้วบางส่วน: จุดสัมผัสเท้า = จุดต่ำสุด (เขย่ง), ระดับพื้นจากเฟรมที่มือสูงชิดผนัง; ยังเป็นค่าเดียวทั้งคลิป | M07 | เปอร์สเปกทีฟของเบาะ |
| จุดยึดสำหรับ load: แยกเท้าลอย (flag) ออกจากเท้าวาง | M11 | เท้าที่ขยับช้าถูกนับเป็นจุดยึด |
| crux แบบ "ฟอร์มพัง" (คะแนนตกแรง) เป็นตัวเลือกที่สอง | M10 | ไอเดียจาก Cruxie |

**เสร็จเมื่อ:** ตัวชี้วัดถึงเป้า v1.0 อย่างน้อย 5 จาก 8 ข้อ และไม่มีข้อไหนแย่ลงจาก baseline

## Phase 4 · ความเร็วและการใช้งาน (1.5–2 สัปดาห์)

1. [x] M02 pose ใน Web Worker (UI ไม่ค้างระหว่างวิเคราะห์) + ปุ่มยกเลิก — pose + กล้องย้ายไป worker ตัวเดียวที่อยู่ตลอดหน้าเว็บ, ส่งเฟรมเป็น ImageBitmap แบบ pipeline; long task ระหว่างวิเคราะห์ 15 → 0, เฟรมละ 51 → 41 ms; ผลเหมือนเดิมทุกค่า; ถ้าใช้ worker ไม่ได้กลับไปวิธีเดิม
2. [~] ความเร็ววิเคราะห์ — วัดแล้ว seek+bitmap แค่ ~10 ms/เฟรม (ซ้อนกับงาน worker อยู่แล้ว) จึงยังไม่ทำ WebCodecs; ตัวช้าคือกล้องที่รันต่อจาก pose → แยก camera worker ทำงานซ้อนกับ pose (เฟรม i ระหว่าง pose ทำ i+1) ผลเหมือนเดิมทุกบิต, Heavy 30 fps เฟรมละ 44 → 33 ms
3. [x] i18n ไทย/อังกฤษ (M17) — ค่าเริ่มต้นตามภาษาเบราว์เซอร์, ปุ่ม TH | EN บนหัวเว็บ (จำค่าไว้), แผงด้านข้างและข้อความสถานะทั้งหมด; กราฟิกบนวิดีโอและคำแนะนำ crux ยังเป็นอังกฤษ (ฟอนต์ไม่มีไทย / รอ Phase 5)
4. [ ] หน้าจอมือถือ: player และแผงควบคุมแบบ bottom sheet
5. [ ] คู่มือถ่ายคลิปในแอป: ตั้งกล้องนิ่ง เห็นทั้งรูท ถ่ายรูปรูทจากจุดเดียวกัน เห็นตัวทั้งตัว
6. [ ] แจ้งเตือนคุณภาพคลิป: ตัวเล็กเกิน, เบลอ, กล้องซูม, จับตัวได้น้อย

**เสร็จเมื่อ:** วิเคราะห์คลิป 40 วิได้ ≤ 45 วิ และผู้ใช้ใหม่ทำครบ flow (โหลด → วิเคราะห์ → export) ได้โดยไม่ต้องอธิบาย

## งานวิจัย/ทางเลือก (หลัง v1.0 หรือขนานกันถ้ามีเวลา)

- โมเดล 133 จุด (RTMPose wholebody) ผ่าน ONNX Runtime Web — เห็นนิ้ว แยกชนิดการจับได้ (crimp/sloper/pinch)
- ท่าทาง 3D (ระยะสะโพกห่างผนัง — สิ่งที่โค้ชดูแต่ภาพ 2D วัดไม่ได้)
- ตรวจโฮลด์สีตามแท็กจากรูปรูท (segmentation สี) แล้วรู้ตำแหน่งโฮลด์ทั้งเส้นก่อนปีน → รู้ว่าโฮลด์ถัดไปคืออันไหนแม่นขึ้น
- จัดรูปรูทที่ถ่ายคนละมุมด้วย homography
- แอปมือถือ (Capacitor/PWA) สำหรับอัดแล้ววิเคราะห์ในเครื่อง

## วิธีทำงาน

- 1 PR = 1 เรื่องเล็ก แตะโมดูลเดียวถ้าเป็นไปได้
- PR ที่แตะ `src/core/**` ต้องแนบผล eval ก่อน/หลัง
- PR ที่แตะ `src/render/**` ต้องแนบภาพเฟรมสำคัญ
- ห้าม commit วิดีโอ (`.gitignore` + เช็กใน CI ว่าไม่มีไฟล์ > 5 MB)
- เลขเวอร์ชัน: v0.3 = จบ Phase 1, v0.4 = Phase 2–3, v0.5 = Phase 4, v0.6 = Phase 5–6, v1.0 = Phase 7
